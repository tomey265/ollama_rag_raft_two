LOW-RAM OLLAMA CONFIGURATION GUIDE — BENCHMARK RESULTS
Machine: Fedora, KDE Plasma, 13GB RAM total, AMD Ryzen integrated GPU (Radeon 680M,
         no ROCm support - confirmed via logs, falls back to CPU-only inference)
Model: hf.co/tomey265/qwen-coder-my:latest (custom quant, Qwen2.5-Coder-14B-Instruct base,
       Q3_K_M quantization, 14.8B params, 32768 max context, 8 KV attention heads / 40 total)
Test prompt used for all runs (kept identical for fair comparison):
"Explain in detail how a hash table works, including collision handling strategies,
and give a Python code example."

Method: for each setting, swap is cleared (`sudo swapoff -a && sudo swapon -a`),
then the model is run once with the test prompt, then `ollama ps` and `free -h`
are captured immediately after the response finishes (before the model unloads).
3 runs per setting. Temperature monitored live via `watch -n 2 sensors` in a
second terminal during later tests.

⚠️ HARDWARE WARNING — read before changing context length

Raising OLLAMA_CONTEXT_LENGTH increases memory use significantly, on top of the
model's own memory footprint. On this test machine (13GB RAM, no dedicated GPU),
setting context length to 16000 caused the Linux kernel's OOM (out-of-memory)
killer to terminate the Ollama process mid-load — confirmed directly in the
system logs (journalctl -u ollama), not just inferred from a crash.

This does NOT mean the whole computer will shut down — the OOM killer targets
the specific process using too much memory, and Ollama auto-restarted seconds
later on its own. But it does mean the model becomes completely unusable at
that setting until context length is lowered again.

Before raising context length on a low-RAM system:
- Check your available RAM first (free -h)
- Increase gradually rather than jumping straight to a large number
- Check `journalctl -u ollama -n 50 --no-pager` if a request fails or hangs —
  an OOM kill will say so explicitly in the log
- Revert the setting immediately if you hit this rather than repeatedly
  retrying, which just repeats the crash

How to revert a systemd context length override:
  sudo rm /etc/systemd/system/ollama.service.d/override.conf
  sudo systemctl daemon-reload
  sudo systemctl restart ollama

TEST 2: OLLAMA_KV_CACHE_TYPE
===========================================
Status: COMPLETE (done), context length limitation noted

OLLAMA_KV_CACHE_TYPE=q8_0, at default context length (4096):
  Run: ollama ps size = 8.3 GB, context = 4096, processor = 100% CPU, swap = 0
  Temperature check: CPU (Tctl) went from ~41°C idle to ~75°C peak during
  generation, back down to ~41°C within minutes after completion. GPU (edge)
  peaked around 60°C. A RAM module sensor (spd5118) briefly tripped its own
  55°C "high" alarm threshold at 58.8°C, well under its 85°C critical limit.
  All values returned to normal promptly after generation ended — consistent
  with normal thermal behavior under load, not a sign of failing cooling.

Result: NO measurable difference vs. baseline at 4096 context.

Likely explanation: at only 4096 context tokens, the KV cache is a small
fraction of total memory (most of the 8.3GB is model weights, ~7.3GB alone).
Quantizing an already-small cache may not move the total enough to register
in ollama ps's reporting. KV cache savings are expected to be more visible
at longer context lengths, where the cache itself is a bigger share of memory.

### OLLAMA_KV_CACHE_TYPE=q4_0

**Result: ~7% RAM reduction (8.3 GB → 7.7 GB) at default context length (4096)**

Unlike `OLLAMA_FLASH_ATTENTION=1` and `OLLAMA_KV_CACHE_TYPE=q8_0` (both of
which showed no measurable difference — see above), the more aggressive
`q4_0` KV cache quantization produced a consistent, repeatable drop in
memory usage.

#### Method

Same fixed test prompt and procedure used throughout this guide:
swap cleared (`sudo swapoff -a && sudo swapon -a`) before each run,
`ollama ps` and `free -h` captured immediately after generation
completed, while the model was still resident (before the 5-minute
keep-alive expired).

Setting applied via systemd override:

```bash
sudo tee /etc/systemd/system/ollama.service.d/override.conf << 'EOF'
[Service]
Environment="OLLAMA_KV_CACHE_TYPE=q4_0"
EOF
sudo systemctl daemon-reload
sudo systemctl restart ollama
```

#### Results (3 runs)

| Run | Model Size (`ollama ps`) | Context | Processor | Swap Used |
|-----|--------------------------|---------|-----------|-----------|
| 1   | 7.7 GB                   | 4096    | 100% CPU  | 0 B       |
| 2   | 7.7 GB                   | 4096    | 100% CPU  | 1.0 GiB   |
| 3   | 7.7 GB                   | 4096    | 100% CPU  | 995 MiB   |

**Baseline for comparison** (default settings / `q8_0`, from earlier
tests in this guide): 8.3 GB, context 4096, 100% CPU, no swap.

#### Notes

- The reported model size dropped consistently across all three runs —
  this is a genuine result, not noise.
- Swap usage appeared in runs 2 and 3 but did not climb further between
  them, suggesting general system memory pressure over the course of the
  test session rather than a leak caused by `q4_0` itself. This machine
  has 13 GB total RAM, so background/session memory pressure is expected
  and worth disclosing rather than omitting.
- Output quality across all three runs remained coherent: each response
  correctly explained hash table fundamentals and at least two collision
  resolution strategies (chaining and open addressing), with working
  Python code. No obvious degradation was observed in this limited,
  informal check, despite this model having a relatively high ratio of
  key-value attention heads (8 of 40), which Ollama's own documentation
  notes can make quality more sensitive to aggressive KV cache
  quantization. A more rigorous quality comparison (e.g. scoring against
  a fixed rubric) was not performed and would be a reasonable follow-up.

#### Verification tip learned during this test

`sudo systemctl edit ollama.service` silently saved an incomplete
override file (missing the `Environment=` line, no error shown) on the
first two attempts. Always confirm the override actually took effect
before testing:

```bash
cat /etc/systemd/system/ollama.service.d/override.conf
```

The `tee` + `daemon-reload` + `restart` method above is more reliable.

TEST 3: OLLAMA_CONTEXT_LENGTH
===========================================
Status: IN PROGRESS — real finding, real crash, documented below

Attempted: OLLAMA_CONTEXT_LENGTH=16000, set via systemd override
(/etc/systemd/system/ollama.service.d/override.conf)

Complication encountered (worth including in write-up as its own note):
`sudo systemctl edit ollama.service` initially saved an incomplete override
file (only "[Service]", missing the actual Environment= line) with no error
shown. This silently failed to apply the setting on the first two attempts.
Confirmed by checking:
  cat /etc/systemd/system/ollama.service.d/override.conf
Fixed by writing the file directly instead of through the interactive editor:
  sudo tee /etc/systemd/system/ollama.service.d/override.conf << 'EOF'
  [Service]
  Environment="OLLAMA_CONTEXT_LENGTH=16000"
  EOF
  sudo systemctl daemon-reload
  sudo systemctl restart ollama
Write-up note: tell readers to always verify the override file's contents
with `cat` after editing, rather than assuming systemctl edit worked.

Once correctly applied (confirmed via journalctl showing
OLLAMA_CONTEXT_LENGTH:16000 in the server config, and n_ctx = 16128 during
model load):

RESULT: CRASH. The model load failed. Confirmed via journalctl -u ollama:
  - Model weight buffers loaded: ~4480 MiB + ~2513 MiB (CPU_REPACK) = ~7GB
  - KV cache buffer allocated: 3024 MiB
  - Available system memory at the time: 9.3 GiB
  - "The kernel OOM killer killed some processes in this unit."
  - ollama.service: Failed with result 'oom-kill'
  - Service automatically restarted itself ~4 seconds later (systemd default
    restart behavior) and returned to normal, context length reverted to
    default (4096) after override file was removed.

Conclusion: 16000 context length is NOT safe on this hardware (13GB RAM,
14.8B param Q3_K_M model). The real safe ceiling is somewhere between 4096
(confirmed working) and 16000 (confirmed OOM crash) — not yet narrowed down.

Next step: test an intermediate value (e.g. 8000) to narrow down the actual
safe maximum context length for this model on this machine.

Important distinction for write-up: this OOM event killed the Ollama process
specifically — it did not power off the whole computer. This is a different
and separate issue from an earlier full-system shutdown this user
experienced, which remains unexplained and is NOT confirmed to be caused by
context length or memory pressure. Do not conflate the two in the write-up.

### OLLAMA_CONTEXT_LENGTH — narrowing the safe ceiling

**Result: 8000 is safe; 16000 crashes. Exact ceiling not yet pinpointed.**

Following up on the earlier crash at 16000 (see above — confirmed real
OOM kill via `journalctl`, not inferred), an intermediate value of 8000
was tested to narrow down where the actual safe limit sits.

#### Method

Same fixed test prompt and procedure used throughout. `OLLAMA_KV_CACHE_TYPE`
left unset (default) so context length was the only variable under test.
CPU/GPU temperature monitored live via `watch -n 2 sensors` in a second
terminal throughout, as a standard precaution given the prior crash.

```bash
sudo tee /etc/systemd/system/ollama.service.d/override.conf << 'EOF'
[Service]
Environment="OLLAMA_CONTEXT_LENGTH=8000"
EOF
sudo systemctl daemon-reload
sudo systemctl restart ollama
```

#### Results (2 runs)

| Run | Model Size (`ollama ps`) | Context | Processor | Peak Temp |
|-----|---------------------------|---------|-----------|-----------|
| 1   | 9.2 GB                    | 8000    | 100% CPU  | ~60°C (Tctl) |
| 2   | 9.2 GB                    | 8000    | 100% CPU  | not separately logged |

No crash, no OOM event, no errors in either run. Temperatures stayed
well under the 85°C critical threshold noted in `sensors` output.

#### Comparison across tested context lengths

| Context Length | Result | Model Size |
|-----------------|--------|-----------|
| 4096 (default)  | ✅ Works | 8.3 GB |
| 8000             | ✅ Works (2 consistent runs) | 9.2 GB |
| 16000            | ❌ Crashes (confirmed OOM kill) | N/A — never finished loading |

#### Notes

- The safe ceiling on this machine (13 GB RAM, no usable GPU offload) is
  somewhere **between 8000 and 16000** — not yet narrowed further. A
  reasonable next step for anyone reproducing this would be testing a
  midpoint (e.g. 12000), which was not performed here due to time
  constraints.
- As before, available system memory dropped significantly while the
  model was loaded (available RAM fell to ~2.2 GB during generation),
  and modest swap usage was observed. This is expected on a 13 GB
  machine running a ~7–9 GB model and is not itself evidence of a
  problem — it only becomes a problem if it triggers an actual OOM kill,
  which did not happen at 8000.

TEST 4: OLLAMA_NUM_PARALLEL
===========================================
Status: COMPLETED

### OLLAMA_NUM_PARALLEL=2

**Result: 2 concurrent requests complete successfully — no crash — at the cost of slower per-request completion time (CPU-bound tradeoff)**

Unlike the earlier single-request tests, `OLLAMA_NUM_PARALLEL` only shows
its effect under concurrent load, so this test was run differently:
two identical requests were fired at the same time (backgrounded shell
jobs) instead of one sequential request.

#### Method

`OLLAMA_KV_CACHE_TYPE` and `OLLAMA_CONTEXT_LENGTH` left at defaults so
`OLLAMA_NUM_PARALLEL` was the only variable under test. Same fixed test
prompt used for both concurrent requests. CPU/GPU temperature monitored
live via `watch -n 2 sensors` throughout, as a standard precaution.

```bash
sudo tee /etc/systemd/system/ollama.service.d/override.conf << 'EOF'
[Service]
Environment="OLLAMA_NUM_PARALLEL=2"
EOF
sudo systemctl daemon-reload
sudo systemctl restart ollama
```

Two requests launched concurrently:

```bash
ollama run hf.co/tomey265/qwen-coder-my:latest "<test prompt>" > /tmp/run1.txt 2>&1 &
ollama run hf.co/tomey265/qwen-coder-my:latest "<test prompt>" > /tmp/run2.txt 2>&1 &
wait
```

#### Results (2 rounds, 2 concurrent requests each)

| Round | Request | Total Time | Tokens | Result |
|-------|---------|-----------|--------|--------|
| 1     | A       | 5m16s     | 1021   | ✅ Success |
| 1     | B       | (not separately logged, completed successfully) | — | ✅ Success |
| 2     | A (slot 0) | 3m41s  | 673    | ✅ Success |
| 2     | B (slot 1) | 4m15s  | 798    | ✅ Success |

Model size while both requests were active: **9.2 GB** (context 4096).

Server logs in round 2 confirmed two distinct processing slots (`slot id
0` and `slot id 1`) were actually used concurrently, verifying that
`OLLAMA_NUM_PARALLEL=2` was genuinely in effect and not just accepted
silently without changing behavior.

#### Comparison to sequential baseline

| Mode | Per-request time | Notes |
|------|-------------------|-------|
| Sequential (1 request at a time) | ~3–4 min | Baseline from earlier single-run tests |
| Parallel (2 concurrent, `NUM_PARALLEL=2`) | ~3m41s–5m16s per request | Both requests still complete, but each takes somewhat longer |

### OLLAMA_MAX_LOADED_MODELS=2

**Result: Two different models (generation + embedding) successfully coexist in memory without eviction**

Unlike `OLLAMA_NUM_PARALLEL` (concurrent requests to the *same* model),
this setting controls how many *different* models Ollama will keep
resident simultaneously — directly relevant to RAG-style workflows
(see Repo 1) that need both a generation model and an embedding model
available without constant reload overhead.

#### Method

`OLLAMA_NUM_PARALLEL` and `OLLAMA_CONTEXT_LENGTH` left at defaults so
`OLLAMA_MAX_LOADED_MODELS` was the only variable under test.

```bash
sudo tee /etc/systemd/system/ollama.service.d/override.conf << 'EOF'
[Service]
Environment="OLLAMA_MAX_LOADED_MODELS=2"
EOF
sudo systemctl daemon-reload
sudo systemctl restart ollama
```

Procedure: load the generation model (`hf.co/tomey265/qwen-coder-my:latest`)
with the standard fixed test prompt, confirm it's resident via
`ollama ps`, then load the embedding model (`nomic-embed-text:latest`)
on top of it with a simple test string, and check whether both remain
loaded or the first gets evicted.

#### Results (2 runs)

| Run | Models Resident | Sizes | Result |
|-----|------------------|-------|--------|
| 1   | qwen-coder + nomic-embed-text | 8.3 GB + 376 MB | ✅ Both loaded, no eviction |
| 2   | qwen-coder + nomic-embed-text | 8.3 GB + 376 MB | ✅ Both loaded, no eviction |

Server logs confirmed `loaded runners count=2` in both runs, and the
embedding model returned a valid 768-dimension embedding vector each
time — confirming it wasn't just "listed" as loaded but actually
functional alongside the generation model.

#### Memory headroom

| Run | Available RAM (both models loaded) |
|-----|--------------------------------------|
| 1   | 9.5 GiB |
| 2   | 2.7 GiB |

The drop in run 2's available memory is most likely attributable to
general session memory pressure that built up over the course of the
day's testing (swap usage had been gradually climbing across earlier
tests too), not something caused by `MAX_LOADED_MODELS` itself. No
crash or OOM event occurred in either run.

#### Notes

- This is a clean positive result: on this machine, running the
  generation model + embedding model together only costs ~376 MB extra
  over the generation model alone — well within budget even under
  memory pressure.
- This setting is directly useful for RAG pipelines like Repo 1, where
  avoiding repeated model reloads between embedding and generation steps
  saves real time.
- Not tested here: behavior when `MAX_LOADED_MODELS` is deliberately set
  too low (e.g. 1) while trying to use two models — this would be a
  reasonable follow-up to demonstrate the eviction behavior this setting
  is meant to prevent.

#### Notes

- No crash, no OOM, no errors in either round. Temperatures stayed safe
  throughout (peaked ~54°C GPU edge / ~61.5°C CPU Tctl — well under the
  85°C critical threshold).
- On this CPU-only, no-GPU-offload hardware, running 2 requests in
  parallel does **not** roughly halve total throughput the way it might
  on a machine with more cores/GPU headroom — each request slows down
  somewhat rather than running at full independent speed, because both
  are competing for the same CPU cycles. This is an expected, honest
  result: `NUM_PARALLEL` buys concurrency (no request has to wait in a
  queue), not free extra throughput, on constrained hardware.
- This tradeoff is worth calling out explicitly for anyone reading this
  guide who might assume "parallel = faster" — on this class of machine,
  it's really "parallel = no queueing, same total work."
